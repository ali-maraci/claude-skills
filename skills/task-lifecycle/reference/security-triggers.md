# Security review trigger (human-readable copy)

The source of truth is `reference/scout.sh` (`SERVER_REGEX`, `CLIENT_SINK_REGEX`, `LOG_PII_REGEX`, `TRIGGER_PATHS` and the two exclude lists). Edit there; this file explains the intent. Check a change with `bash scout.sh <repo> <sha>~1..<sha>` on a few real commits before committing it.

The trigger is **mechanical**: the builder or fix builder that just committed runs `scout.sh <repo> <range>` and copies its output (it already has the repo open, so no separate agent is paid for; a Haiku scout agent runs it only when a builder returns no usable measurement). The script uses `/usr/bin/grep -E` throughout, because a BRE `grep -v '^\+\+\+'` is rejected by BSD grep and ugrep and the content triggers below then silently never run. There is no "when unsure, fire" judgement. The security reviewer runs as an extra Opus agent when **any** of these fires on the review range:

- **Path triggers** (any changed path, substring match). Built in: `auth/`, `webhooks/`, `migrations/`, `db/`, `deploy`, `gdpr`, CI workflows (`.github/workflows/`), infra (`Dockerfile`, `terraform`, `cdk`), and new or bumped dependencies (`package.json`, lockfiles, `requirements*`). Add your own with `.claude/security-trigger-paths` in the repo under review: one substring per line, blank lines and `#` comments ignored.
- **Server-side content trigger.** Added lines in files that are not client views (`*.tsx`, `*.jsx`, `*.css`, `*.scss`, `*.html`, `**/components/**`) and not noise (lockfiles, snapshots, generated, `*.test.*`, `*.spec.*`, `__tests__`, fixtures, `*.md`, `*.svg`) matching: auth helpers and session or cookie writes, JWT, passwords, secrets, API keys, PIN, audit tables, GDPR, raw SQL execution (`execute(`, `cursor.execute`, bare `text(` but not `.text(`), webhooks, CORS/CSP, IAM/KMS, cloud and LLM calls, presigned URLs, **route definitions** (Flask `@bp.route`/`@app.get`, Next `export async function GET|POST…`, Express `router.post(`, `"use server"`), and **authorisation words** (`is_admin`, `authorize`, `has_permission`, `check_access`, `permission`). Add your own with `.claude/security-trigger-regex` in the repo under review: one ERE per line (non-comment lines are joined with `|`), OR-ed into this regex. Typical entries are the names of your personal-data fields and audit helpers. Empty alternatives (a stray `|`) are dropped; if what is left is not a valid ERE, or matches an empty line, it is ignored and the trigger fires with `REASON: config: invalid .claude/security-trigger-regex`, so a typo never switches the content trigger off.
- **Client-sink trigger** (all non-noise files): `dangerouslySetInnerHTML`, `localStorage`, `sessionStorage`, `document.cookie`, `innerHTML`, `eval(`, `new Function(`, `window.open(`, `postMessage(`.
- **Log-PII trigger** (all non-noise files): a `console|logger|logging|log .(log|info|warn|error|debug|exception)(` call on the same added line as `token`, `pin`, `password`, `secret` or `authorization`.

Every match is recorded as a reason (`path: …` or `line: …`, capped at 40 lines per grep) and the first dozen are handed to the security reviewer. When nothing fires, the PR body records `Security review: skipped — no path/content trigger on <range> (<n> files, <m> lines)`.

## Why it is shaped this way

Matching bare words like `auth|session|token|upload` anywhere in the diff hits `useSession`, import paths and prop names in almost every web file, so the security review ran in every round of every run, including copy-only UI changes. Narrowing the words was not enough: `.text(` matched every `await res.text()`, lockfiles were grepped, domain nouns in UI copy matched, and asking a Haiku agent to judge endpoint and authorisation changes from the raw diff with "when unsure, fire" brought the over-firing back. The current design matches definitions and sinks in server-side code, a short explicit list of client sinks, and sensitive words next to log calls; endpoint and authorisation changes are regex patterns, not judgement.

Known gaps, accepted: a client-only XSS via a sink not in the list; a server file under an unusual extension — including a `"use server"` action inside a `.tsx` file, which the client-view exclusion hides from the server-side grep; domain-noun copy changes (intentionally not a trigger). Your repo's human-review rules still apply to the PR.
